# KVE-2026-2513 KCP 현금영수증 처리 권한 및 정합성 보완

작성일: 2026-10-14

## 원인과 영향 범위

`shop/kcp/pp_cli_hub.php`는 발급 화면의 주문 소유권 검증을 거치지 않은 직접 요청에도 클라이언트의 금액과 거래번호로 KCP 거래를 수행했다. 미존재 주문에 대한 UPDATE가 0행을 변경한 경우에도 SQL 실행 성공만 확인하여 외부 승인 취소가 생략될 수 있었다.

로컬 Git 태그 `v5.6.36`, `v5.6.37`, `v5.6.38`, `v5.6.39`, `v5.6.39.1`, `v5.6.40`, `v5.6.41`, `v5.6.42`의 처리 파일은 동일한 SHA-256 `75d169648957ce9f0837214a99c8920292535f870fd08a7c52a02d70359d9b31`을 가진다. 이는 해당 태그들의 정적 코드 영향 확인이며, 각 버전의 설치·연동을 모두 재현한 결과는 아니다. 더 이전 버전도 같은 코드가 존재할 수 있으며 최초 유입 버전은 확정하지 않았다.

## 변경 사항

- 실제 주문/개인결제의 존재와 공통 소유권 검사 통과 후에만 발급한다. 최고관리자도 존재하지 않는 주문이나 미수납 주문은 발급할 수 없다.
- POST 발급만 허용한다. 현재 화면에서 사용하지 않는 공개 조회·취소 요청은 거절한다. 저장 실패 시 해당 요청에서 승인받은 거래를 취소하는 내부 보상 처리는 유지한다.
- 세션·주문 유형·주문번호·발급 작업에 묶인 10분 일회용 토큰을 검사한다. 동일 주문 화면을 다시 열면 앞서 열린 화면의 토큰은 만료된다.
- 요청의 금액·주문자·상품·가맹점 정보를 사용하지 않고 원장과 서버 설정에서 구성한다. 식별번호와 발급 용도만 형식을 검사하여 받는다.
- 수납·환불·미수금·결제수단·발급 설정·PG를 확인한다. 일반 주문은 서버의 공급가액/면세액/세액 합계와 순수납 금액이 정확히 일치해야 한다. 부분환불 후 과세 정보가 불일치하면 임의 비율로 계산하지 않고 관리자 확인을 요청한다.
- 개인결제는 전액 수납된 독립 결제만 허용한다. 다른 주문에 연결된 개인결제는 주문 화면에서 처리하도록 한다.
- 외부 통신 전 조건부 UPDATE로 `cash_info`에 처리 중 표식을 저장한다. 같은 주문의 다른 세션 요청과 프로세스 중단 후 재요청도 이 영속 표식으로 차단한다. 추가 테이블이나 스키마 마이그레이션은 필요하지 않다.
- 저장 시 원장 금액/상태와 영향 행 수를 다시 확인한다. 저장 실패는 이번 승인에 한해 보상 취소한다. 보상 취소 실패나 통신 결과 불명은 재조정 상태로 남긴다.
- 처리 결과는 서버 세션에서 표시한다. 외부 POST로 성공 화면이나 거래번호를 위조할 수 없으며 출력 문자열을 HTML 이스케이프한다.
- 관리자 주문/개인결제 화면에서 처리 확인이 필요한 상태를 표시한다. 감사 로그에는 처리 확인번호와 상태만 남기며 개인 식별번호·가맹점 키·PG 응답 원문은 남기지 않는다.
- PHP 8.4에서 KCP CLI 객체의 동적 속성 생성 경고가 발생하지 않도록 누락된 속성 두 개를 선언한다.

## 확인 대기 거래의 운영 처리

`od_cash_info` 또는 `pp_cash_info`의 직렬화 배열에 `kcp_cash_state=pending` 또는 `reconcile`이 있으면 자동 재발급하지 않는다. 상태에는 처리 확인번호(`attempt`), 요청 시각, 금액이 기록되며, 보상 취소 실패 시 확인된 KCP 거래번호도 저장한다. 정상 발급의 기존 `cash_no`/`cash_info` 구조는 유지한다.

1. 관리자 화면의 확인번호와 해당 주문번호·금액·요청 시각으로 KCP 가맹점 관리자에서 거래 유무와 취소 여부를 대조한다.
2. 원장 저장만 실패하고 KCP 승인이 유지된 경우, 실제 거래에 맞춰 원장을 복구하거나 KCP에서 해당 승인만 취소한다. 다른 정상 거래를 취소하지 않는다.
3. 발급이 없거나 취소가 확정된 뒤에만 담당자가 해당 주문의 처리 중 표식을 해제한다. 조치 전후 원장과 KCP 확인 결과를 보관한다. 단순한 타임아웃이나 경과 시간만으로 해제하지 않는다.
4. DB 장애 등으로 상태 기록이 실패했으면 서버의 `KCP cash <확인번호> <상태>` 로그와 KCP 거래 내역을 함께 확인한다. SQL 오류나 PG 오류 코드를 정상 발급 완료로 취급하지 않는다.

KCP가 오류를 반환한 경우에도 통신 실패와 승인 여부를 혼동하지 않도록 보수적으로 확인 대기 상태를 유지한다. 따라서 잘못된 가맹점 설정이나 명시적 거절도 관리자 확인 후 재시도가 필요할 수 있다.

## 검증 방법

운영 설정이나 운영 DB를 읽지 않는 별도 MySQL 인스턴스에서 실행한다. 테스트 소켓 경로는 `/tmp/kve2513-`로 시작해야 한다.

```sh
php7.4 tests/kcp_cash_test.php /tmp/kve2513-검증경로/mysql.sock
php8.4 tests/kcp_cash_test.php /tmp/kve2513-검증경로/mysql.sock
python3 tests/kcp_cash_http.py /tmp/kve2513-검증경로/mysql.sock
```

DB 테스트는 MyISAM/InnoDB, 회원/비회원/최고관리자, 미존재/타인 주문, 입력·토큰 변조, 개인결제, 부분환불·복합과세, SQL/0행/비정상 행 수, 보상 취소 실패, 응답 유실, 동시 4세션, 프로세스 종료 후 재발급 차단을 확인한다. HTTP 테스트는 실제 처리 PHP 파일과 별도 원장을 사용하고 전송 클래스만 모의 구현으로 대체한다.

실제 KCP 테스트 거래는 다음과 같이 명시적으로 실행한다. 테스트 코드에 지정된 공용 테스트 가맹점만 사용하고, 운영 설정은 로드하지 않는다. 1,000원 승인 후 `finally`에서 같은 거래를 즉시 전액 취소한다. 취소 실패 시 격리 작업 디렉터리의 `kcp-test-cleanup-required.json`을 확인하고 테스트 거래를 정리한다.

```sh
php8.4 tests/kcp_cash_live_test.php /tmp/kve2513-검증경로/mysql.sock --confirm-kcp-test-mode
```

2026-10-14 KCP 테스트 게이트웨이의 승인 응답 `0000`, 원장 저장, 전액 취소 응답 `0000`을 확인했다. 최초 시험에서 확인한 PHP 8.4 동적 속성 경고를 보완한 후 재시험에서도 승인·취소가 정상 완료되었다. 운영 가맹점이나 실제 고객 데이터는 사용하지 않았다.

## 적용 및 보고

처리 파일·발급 화면·결과 화면·공통 라이브러리·관리자 안내를 함께 배포한다. 이전 발급 화면에 토큰이 없으면 요청이 거절되므로 화면을 새로 열어야 한다. 배포 전 진행 중 발급이 없는지 확인하고 유지보수 창에서 파일 세트를 교체한다. 롤백 시에도 처리 중 표식은 삭제하지 않으며, 기존 취약 처리 경로를 외부에 다시 열지 않는다.

이 변경 자체는 공개 배포 버전 번호를 올리거나 KISA에 문서를 발송하지 않는다. 수정 커밋, 시험 결과, 공개 배포 버전/일자 및 제출 담당자를 구분하여 이슈에 기록한다. KISA 제출 시 운영 피해가 입증되었다거나 모든 과거 버전에서 동적 재현했다고 표현하지 않는다.

참고: [KCP 현금영수증 발급 문서](https://developer.kcp.co.kr/reference/cash-issue). 신규 HTTP API 문서와 기존 CLI 전송 방식은 다르므로 이번 변경에서 연동 방식을 교체하지 않았다.

## 재검증 발견 사항 보완

개인결제에는 `mb_id`가 없으므로 일반 주문에만 회원 필드 조건을 적용한다. 독립 개인결제의 연결 주문번호는 정수 `0`으로 비교하며, 개인결제 접근 권한은 기존 주문조회 세션 또는 최고관리자 권한으로 확인한다.

발급 저장의 응답이 유실되면 이번 시도 식별자와 거래번호, 원장 금액을 다시 조회한다. 저장이 확인되면 불필요하게 취소하지 않는다. 취소가 필요한 경우에는 이번 처리 중 표식 또는 이번 시도에서 저장한 승인만 확인 필요 상태로 전환한 뒤 KCP를 호출한다. 상태 전환을 확인하지 못하면 외부 취소를 시작하지 않는다. 취소 실패는 관리자 경고를 유지하고, 취소 성공은 해당 표식만 제거한다.

회귀 테스트는 일반 주문과 개인결제 테이블을 설치 SQL에서 직접 생성한다. 실제 저장 후 false/예외 반환, 저장 후 금액 변경, 보상 취소 성공/실패를 모두 검사하며 반환값뿐 아니라 최종 cash/cash_no/cash_info와 관리자 경고도 확인한다.
